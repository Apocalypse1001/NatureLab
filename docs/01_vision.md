# NatureLab — Interactive Physical Behavior Simulator

## Общая задача

Необходимо разработать и развивать проект **NatureLab** — интерактивный образовательный симулятор поведения физических систем и природных процессов.

Это НЕ заранее записанная анимация и НЕ обычная 3D-игра.

Основная идея проекта:

> Пользователь изменяет условия окружающего мира, после чего физический движок самостоятельно рассчитывает последствия этих изменений.

Поведение воды, объектов, деревьев, автомобилей, мусора, грунта и других элементов не должно быть заранее прописано сценарием вида:

```text
через 3 секунды машина двигается;
через 5 секунд дерево падает;
через 8 секунд вода исчезает.
```

Вместо этого должно быть:

```text
изменились физические условия
        ↓
изменилась сила воздействия
        ↓
изменилась скорость объекта
        ↓
объект начал двигаться
        ↓
столкнулся с другим объектом
        ↓
изменил окружающую среду
        ↓
это повлияло на дальнейшее развитие симуляции
```

То есть NatureLab должен быть **симулятором поведения системы и причинно-следственных связей**.

---

# Главная образовательная цель

Проект предназначен в первую очередь для детей и обучения через эксперимент.

Ребёнок должен не просто увидеть красивое наводнение или вулкан.

Он должен иметь возможность спросить:

- Что будет, если поднять дом выше?
- Что произойдёт, если поставить автомобиль ближе к реке?
- Что произойдёт, если построить стену?
- Куда пойдёт вода?
- Почему машина начала двигаться?
- Почему одно дерево упало, а другое осталось?
- Почему вода после препятствия изменила направление?
- Что будет, если изменить русло реки?
- Что произойдёт, если сузить канал?
- Что будет, если увеличить или уменьшить уклон?
- Почему в одном месте происходит эрозия, а в другом осаждение грунта?

Пользователь должен иметь возможность:

```text
создать условия
        ↓
запустить эксперимент
        ↓
наблюдать последствия
        ↓
изменить один параметр
        ↓
запустить эксперимент снова
        ↓
сравнить результаты
```

Основная образовательная модель:

# ГИПОТЕЗА → ЭКСПЕРИМЕНТ → ФИЗИКА → РЕЗУЛЬТАТ → ОБЪЯСНЕНИЕ

# Что должен представлять собой NatureLab

Это должна быть интерактивная 3D-песочница.

Например, пользователь видит участок территории:

```text
────────────────────────────
           река

~~~~~~~~~~~~~~~→→→→→→→

        🌳
   🏠        🚗
        📦
🌳                🏠
────────────────────────────
```

Пользователь может мышкой:

- изменять рельеф;
- поднимать и опускать землю;
- ставить дома;
- изменять высоту фундамента дома;
- добавлять автомобили;
- добавлять деревья;
- добавлять коробки и другие предметы;
- строить препятствия;
- удалять объекты;
- изменять положение объектов;
- менять характеристики среды;
- запускать и останавливать симуляцию.

После нажатия START пользователь больше не управляет результатом напрямую.

Дальнейшее состояние мира должно определяться физической моделью.

# Первый основной модуль — FloodLab

Первый полноценный сценарий NatureLab — **симуляция наводнения**.

Необходимо моделировать:

- движение воды по рельефу;
- глубину;
- направление;
- скорость потока;
- заполнение низин;
- движение воды вокруг препятствий;
- воздействие воды на предметы;
- плавучесть;
- сопротивление;
- трение;
- движение предметов;
- столкновения;
- остаточное состояние мира после ухода воды.

Пример:

```text
НАЧАЛО

🏠       🌳        🚗

          ↓

приходит поток воды

~~~~~~~~~~~~~~→→→→

          ↓

коробка начинает плавать
машина начинает скользить
дерево испытывает нагрузку

          ↓

дерево падает

          ↓

падение дерева создаёт новое препятствие

          ↓

поток воды меняется

          ↓

машину относит в другое место
```

Важно:

**каждый следующий результат должен возникать из предыдущего состояния физической системы.**

---

# Вода не должна быть декоративной анимацией

Это одно из главных требований проекта.

Если пользователь изменил:

- terrain;
- препятствие;
- глубину воды;
- скорость;
- русло;
- дамбу;

вода должна изменить своё поведение.

Нельзя использовать заранее подготовленный путь движения воды.

Например:

```text
вариант A:

        HOUSE
          █
→→→→→→→→ █
          █
       ↘
         ↘
```

Если пользователь передвинул дом:

```text
вариант B:

             HOUSE
               █
→→→→→→→→→→     █

```

траектория потока также должна измениться.

# Очень важный принцип

## Simulation State является источником истины.

Не Three.js.

Если автомобиль визуально находится здесь:

```text
X=12
Z=20
```

то backend должен знать:

```text
CAR_004
position = [12, ..., 20]
```

Если дерево сломалось:

```text
TREE_007
state = BROKEN
```

Если машина плывёт:

```text
CAR_004
state = FLOATING
```

Frontend только отображает это состояние.

# Частицы

Частицы должны использоваться там, где они действительно соответствуют физической модели.

Необходимо избегать подхода:

> «нарисуем миллион красивых частиц и назовём это физической водой».

Если частицы участвуют в физике:

- положение;
- скорость;
- масса;
- плотность;
- взаимодействие;
- соседство;

должны рассчитываться физическим solver.

Если частицы используются только как визуальный эффект:

```text
брызги
пена
капли
дым
пепел
искры
```

они должны быть явно отделены от основного simulation state.

Например:

```text
REAL WATER PHYSICS
        ↓
height field
velocity field
pressure
flow direction
        ↓
Three.js
        ↓
visual particles
foam
spray
waves
```

То есть визуальный эффект не должен определять физический результат.

# Основная модель воды

Для наводнений предпочтительно использовать GPU shallow-water simulation или другую подходящую физическую модель.

Основное поле воды должно иметь:

```text
water depth
velocity X
velocity Z
surface height
terrain height
obstacles
```

Например каждая клетка:

```text
terrain = 1.25 m
water depth = 0.72 m
velocity X = 2.4 m/s
velocity Z = 0.3 m/s
```

Необходимо обеспечивать:

- conservation of water;
- корректные boundary conditions;
- стабильность solver;
- отсутствие появления воды из ниоткуда;
- отсутствие phantom water внутри solid objects;
- корректное взаимодействие с terrain.

# Поведение автомобиля

Автомобиль не должен начинать движение просто потому, что:

```text
water_depth > 0.5
```

Нужно учитывать физические силы.

Пример:

```text
             buoyancy
                 ↑

water drag ← [ CAR ]

                 ↓
               weight

         + ground friction
```

Использовать как минимум:

```text
gravity
buoyancy
hydrodynamic drag
ground friction
mass
```

Результат:

```text
маленькая лёгкая коробка
        ↓
начинает двигаться раньше

тяжёлая машина
        ↓
остаётся дольше

увеличивается поток
        ↓
машина начинает скользить

увеличивается уровень
        ↓
частично теряется контакт с дорогой

        ↓
машина начинает плавать
```

# Последствия должны сохраняться

После ухода воды мир НЕ должен автоматически возвращаться в исходное положение.

Например:

до:

```text
🌳          🚗
     📦
🏠              🌳
```

после:

```text
    🪵

              🚗
 📦       📦

🏠        broken fence
```

Когда вода уходит:

- машина опускается на землю там, куда её принесло;
- коробки остаются;
- дерево остаётся лежать;
- обломки остаются;
- повреждённые объекты сохраняют состояние.

И только RESET возвращает первоначальный мир.

# Cause & Effect system

Это ключевая образовательная функция.

Нужно сохранять важные события.

Например:

```text
12.41 sec
CAR_003
STARTED_MOVING

Cause:
water depth = 0.46 m
flow velocity = 1.8 m/s
drag force = ...
ground friction = ...
```

Следующее:

```text
14.17 sec
CAR_003
FLOATING
```

Следующее:

```text
18.42 sec
CAR_003
COLLISION
TREE_014
```

Следующее:

```text
18.45 sec
TREE_014
BROKEN
```

В дальнейшем пользователь должен иметь возможность выбрать объект и спросить:

# «Почему это произошло?»

Система сможет показать цепочку:

```text
уровень воды вырос
        ↓
уменьшилась сила контакта машины с землёй
        ↓
drag превысил friction
        ↓
машина начала двигаться
        ↓
машина столкнулась с деревом
        ↓
нагрузка на дерево превысила предел
        ↓
дерево сломалось
```

Это одна из главных целей NatureLab.

# Viktor Schauberger Lab

В дальнейшем желательно создать отдельный экспериментальный режим, связанный с идеями Виктора Шаубергера о поведении воды и форме русла.

Важно:

не считать идеи автоматически правильными.

NatureLab должен использовать научный подход:

```text
HYPOTHESIS
 ↓
BUILD
 ↓
SIMULATE
 ↓
MEASURE
 ↓
COMPARE
```

Например:

```text
River A
обычное русло

River B

```

```text

erosion
sediment
turbulence
energy losses

```

То есть ребёнок не получает утверждение:

> «эта идея правильная».

> «давайте построим и проверим».

# Масштабируемость

Основная целевая GPU:

**NVIDIA RTX 5090 32 GB**

Но проект должен иметь CPU fallback для разработки на других компьютерах.

Режим:

```text
AUTO
CUDA
CPU
```

AUTO:

```text
CUDA available
→ Warp CUDA

CUDA unavailable
→ CPU fallback
```

CPU version не обязана быть быстрой.

Она нужна для:

- frontend development;
- UI;
- editor;
- маленьких simulation grids;
- тестов;
- разработки на рабочем компьютере.

GPU версия должна использоваться для больших физических экспериментов.

# Очень важное GPU-требование

Минимизировать:

```text
GPU → CPU → GPU
```

Основная физика должна оставаться на GPU.

Например:

```text
Warp GPU
│
├── water solver
├── sample water at body positions
├── calculate force
├── rigid-body update
└── collision logic
```

CPU/Three.js должны получать главным образом данные, которые нужны для визуализации:

```text
water height map
velocity visualization
object transforms
events
terrain changes
```

Не копировать миллион частиц с GPU на CPU 60 раз в секунду без необходимости.

---

# Simulation timestep

Физика не должна зависеть от FPS Three.js.

Например:

```text
Three.js rendering
60 / 120 FPS

Physics
fixed timestep
```

FluidSolver должен иметь возможность выполнять внутренние substeps:

```text
simulation tick
      ↓
fluid substep
fluid substep
fluid substep
      ↓
rigid-body update
```

Использовать CFL condition или другое подходящее ограничение устойчивости.

# Уровень реализма

NatureLab не обязан становиться сертифицированным инженерным CFD-пакетом.

Цель:

> физически правдоподобная, воспроизводимая и понятная образовательная симуляция.

Необходимо избегать ложной точности.

Если какая-либо модель упрощена, это должно быть явно указано.

Но причинно-следственные связи должны соответствовать реальной физике настолько хорошо, насколько позволяет выбранная модель.

# Главный критерий качества

Правильность проекта нельзя оценивать только по тому, насколько красиво выглядит вода.

Главный тест:

# Изменение причины должно физически корректно изменять следствие.

Например:

```text
машина стала тяжелее
→ её сложнее сдвинуть

вода стала быстрее
→ hydrodynamic force увеличилась

дом переместили
→ поток изменился

канал сузили
→ изменились скорость/уровень

изменился terrain
→ изменилась траектория воды

дерево упало
→ оно стало новым препятствием
→ поток изменился ещё раз
```

Если результат остаётся тем же независимо от изменения физических условий — симуляция реализована неправильно.

# Требования к разработке

При получении существующего архива проекта:

1. сначала провести аудит;
2. изучить README;
3. изучить ARCHITECTURE;
4. изучить CURRENT_STATUS;
5. изучить TODO;
6. запустить тесты;
7. определить текущую стадию;
8. не переписывать рабочую архитектуру без серьёзной причины.

Для каждого обнаруженного физического или архитектурного недостатка:

```text
описать проблему
↓
объяснить последствия
↓
предложить решение
↓
добавить regression test
↓
только после этого исправлять
```

Особое внимание уделять:

- conservation;
- symmetry;
- stability;
- boundaries;
- GPU/CPU synchronization;
- determinism;
- object-fluid coupling;
- performance;
- физической интерпретации результатов.

# Приоритет проекта

Приоритеты строго следующие:

```text
1. Правильная архитектура
2. Физическая причинность
3. Стабильность solver
4. Воспроизводимость
5. Производительность GPU
6. Удобство редактора
7. Образовательный слой
8. Красивые визуальные эффекты
```

Не менять этот порядок.

Красивую воду можно сделать позже.

Неправильную физику, спрятанную под красивым Three.js shader, считать провалом проекта.

# Конечная идея NatureLab

NatureLab должен стать:

> интерактивной лабораторией физического мира, где ребёнок не получает готовый ответ, а изменяет окружающую среду, запускает эксперимент и самостоятельно наблюдает, почему одно действие вызывает другое.

Первый этап:

**FloodLab**

Далее:

**RiverLab**

Далее:

**VolcanoLab**

В дальнейшем:

- erosion;
- landslide;
- weather;
- ecosystems;
- другие природные процессы.

Но всё должно использовать общий принцип:

# МИР → ФИЗИКА → ПОВЕДЕНИЕ → ПОСЛЕДСТВИЕ → ПОНИМАНИЕ

Именно это является основной целью проекта NatureLab.
